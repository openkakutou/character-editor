# Palette editor stores colors in semantic MUGEN index order; one shared function converts to/from `.act` file order

**Context:** Backlog item 005 needs an in-editor representation of a 256-color palette. The `sff` Go library's `DecodeExternalPalette`/`EncodeExternalPalette` (called by the WASM bridge whenever `resolveSpritePixels` is given an override palette, and the authority for what a real `.act` file's byte layout means) reverses index order: a raw `.act` file's byte position `i` (0..255) holds the color for **palette index `255-i`**, not index `i` — and index 0 (the one a sprite's pixel value 0 always resolves to) is forced fully opaque-transparent by that decode, regardless of what RGB value sits there.

**Decision:** The editor's own in-memory palette (`palette.ts`) stores its 256 colors in **semantic MUGEN index order** — index `k` is the same `k` a sprite pixel value resolves to — never raw file-byte order. Index 0 is UI-flagged as reserved: not editable-with-a-warning, but explicitly informational ("always fully transparent in-game, this color has no visual effect"), since the Go decode enforces that unconditionally, not as a risk the user could realize by editing it. Exactly one function, `reversePaletteByteOrder`, converts between the two orders — proven a mathematical involution (`raw[i] = semantic[255-i]`; applying it twice returns the original), so the same function serves both directions and both call sites that need file order: building the WASM bridge's `overridePaletteBytes` argument for the live preview, and serializing a downloadable `.act` file. Uploading an existing `.act` file to edit runs the same conversion immediately on read, so the in-memory model is never in file order. A 772-byte upload (the common Adobe-exported variant carrying a 4-byte trailing color-count/transparency-index footer) is detected and normalized to 768 bytes before this conversion; any other length is rejected with a descriptive error at the upload boundary, before it can reach the WASM bridge.

**Reason:** Semantic order matches every other domain concept this app already uses (a Sprite's `palette`/pixel-index fields, the well-known MUGEN convention that index 0 is the transparent slot) — editing "index 0" in the UI means the same index 0 a domain expert already expects. A single shared conversion function, rather than one hand-written loop per call site, forecloses the classic bug of two subtly different reversal formulas (e.g. one off-by-one variant) silently shifting colors by one slot between the live preview and the exported file. Validating the upload's byte length in the editor itself — rather than relying on the WASM module's own generic length-mismatch error — keeps a malformed upload from ever reaching (and be rejected deep inside) the `resolveSpritePixels` call at all.

**Rejected alternatives:**
- *Store the palette in raw file-byte order internally*: rejected — every read/write of "index k" throughout the UI would then need its own reversal, and "index 0" in the UI would silently mean file position 0 (semantic index 255), not the well-known transparent slot a domain expert expects.
- *Two separate conversion functions, one per call site (export vs. live-preview override)*: rejected — the two are literally the same operation on the same data; hand-writing it twice is exactly the drift risk a shared involution avoids.
- *Treat index-0 editing as a soft warning rather than an informational, always-inert note*: rejected — the Go decode's forced transparency isn't a risk contingent on how the palette is used, it is unconditional on every call (live preview and any real MUGEN/Ikemen load), so framing it as merely risky would understate it.

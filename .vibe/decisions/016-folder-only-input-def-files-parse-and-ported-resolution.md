# Folder-only character input: minimal local `.def` `[Files]` parse ahead of the WASM load call, resolution logic ported from `stage`/`lifebar`

**Context:** Backlog item 014 makes folder selection the web build's only way to load a character, replacing item 002's per-kind file picker/drop zone outright. Referenced `.air`/`.sff`/`.cns`/`.cmd` files must be located by the exact filename the chosen `.def` references, not guessed by extension. Unlike the `stage`/`lifebar` WASM bridges (whose `load` call accepts a `.def`'s bytes alone and returns every referenced filename as part of the parsed result, so their own folder-input items could resolve referenced files *after* loading), the `character` WASM module's `OpenKakutouCharacter.load` requires all four required files' bytes (`.def`/`.air`/`.sff`/`.cns`) simultaneously — there is no WASM call that parses just the `.def`'s referenced filenames ahead of having the other three already in hand.

**Decision:**
- A small, narrowly-scoped local text parser (`def-files-section.ts`) reads only the `.def`'s `[Files]` section for the `sprite`/`anim`/`cns`/`cmd` keys — mirroring the `character` Go library's own `def.Parse` key-to-field mapping exactly (confirmed by reading its source) — and nothing else about `.def`'s grammar (comments, `[Info]`, palette/state-file lists) is reimplemented. This runs once, ahead of the real WASM `load` call, purely to learn which filenames to look for in the folder listing.
- Folder gathering (`folder-entries.ts`: `GatheredFile`, the `*Like` entry interfaces, `collectFilesFromEntry`, `filesFromDataTransferItems`, `filesFromWebkitDirectoryFiles`) and referenced-file resolution (basename match, exact case first, case-insensitive fallback second, more than one match reported as ambiguous rather than guessed) are ported near-verbatim from the same pattern already shipped and real-browser-verified in `stage-editor`/`stage-viewer-web`/`lifebar-editor`/`lifebar-viewer-web` — not re-derived, since folder-listing/basename-resolution has no domain specifics of its own. The `.def`-candidate picker UI (native radio inputs, `role="radiogroup"`, a disabled-until-selected confirm button, a "Choose a different folder" reset control) is ported the same way.
- `.zss` has no `[Files]`-section key of its own in the `character` library at all (confirmed by reading its source) — it stays optional and is located by extension only: a single `.zss` file in the folder is used; more than one is reported in the load status but does **not** block loading, following item 002's own established rule that an optional kind's ambiguity/duplicate never blocks an otherwise-complete required set.

**Reason:** The local `[Files]`-section parse is unavoidable given the WASM boundary's actual shape (confirmed by reading `bridge.ts`'s `load()` signature and the Go library's own `def.Parse`), and kept deliberately minimal — 4 keys, one section — rather than a second, competing `.def` parser. Reusing the sibling repos' already-reviewed gathering/resolution/picker code keeps this app's folder-input behavior consistent with the rest of the org instead of a third, subtly different implementation of the same browser-API workarounds (jsdom has no `FileSystemEntry`/`webkitGetAsEntry`, so that logic is modeled as minimal `*Like` interfaces and unit-tested against plain mocks, with real-browser behavior confirmed separately).

**Rejected alternatives:**
- **Extend the WASM bridge with a new "parse `.def` only" call:** rejected as out of this item's scope — a cross-repo WASM surface change belongs to the `character` library's own backlog, not this item, and the local minimal parse is small enough not to justify it.
- **Guess referenced files purely by extension (the old per-kind slot model):** rejected outright — this is exactly what the acceptance criteria rule out.
- **Treat a `.zss` ambiguity as blocking, like a required-kind ambiguity:** rejected — `.zss` is optional, and item 002 already established that an optional kind's ambiguity never blocks an otherwise-loadable character.

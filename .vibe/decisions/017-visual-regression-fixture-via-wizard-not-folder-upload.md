# Visual regression tests drive the app through the New Character Wizard, not a hand-authored folder fixture

**Context:** Backlog item 016 needs baseline screenshots of three real rendered surfaces (the sprite browser, the palette editor's live-recolored preview, the animation editor's Clsn overlay), loaded/edited from real character data, not blank/default state. Every sibling repo that already shipped its own equivalent (`lifebar-editor`, `stage-editor`) drives its suite through a real, purpose-authored folder fixture uploaded via the app's own folder picker. This app's own file input is folder-only (item 014, `.vibe/decisions/016`), so the same approach would require hand-authoring a real `.def` referencing a `.sff`/`.air`/`.cns`/`.cmd`, plus a real sprite sheet with a genuine, non-trivial pixel for the palette editor's recolor to be visible against.

**Decision:** The suite instead drives the app through its own real New Character Wizard (`.vibe/decisions/013`) with the "basic" template — a real user-facing action already covered by this app's own manual real-browser verification (see `docs/testing.md`). The wizard round-trips a brand-new character through the actual `character` WASM save/load path and pairs it with the app's own already-bundled `public/wizard/blank-character.sff` (byte-identical to `src/wasm/testdata/v1-basic.sff`, already a real decoded sprite this repo's own WASM bridge tests pin values against), producing a character indistinguishable from an imported one, with one real sprite (group 0, image 0) and one real animation frame referencing it — sufficient to exercise all three covered surfaces with zero new fixture files.

**Reason:** Avoids hand-writing `.def`/`.air`/`.cns`/`.cmd` text (format knowledge that already lives in `character`, and risks drifting from what its own parser actually accepts — the same reasoning `.vibe/decisions/013` already rejected for the wizard itself) and avoids sourcing/vendoring a second real sprite sheet fixture when the repo already has one, reused verbatim. The wizard path is not a synthetic test-only bypass: it is the app's own real "create a character from scratch" feature, so this suite exercises genuine app code end to end, same as a folder-upload-driven suite would.

**Rejected alternatives:** A hand-authored `.def`/`.sff`/`.air`/`.cns` folder fixture uploaded through the folder picker, mirroring `lifebar-editor`/`stage-editor` — rejected: this app's `.def` `[Files]` section parsing (`.vibe/decisions/016`) and the WASM `loadCharacter` call both need all four files' bytes to be independently well-formed and mutually consistent, which is exactly the risk `.vibe/decisions/013` already avoided for the wizard by round-tripping through the real WASM save path instead of hand-writing text; reusing the wizard sidesteps the same risk here for free. A brand-new sprite sheet fixture crafted specifically for this suite — rejected: `v1-basic.sff`/`blank-character.sff` already exists, is already a real decoded sprite with non-trivial pixel data (confirmed by decoding it once against a synthetic index-mapped palette to find its dominant palette index for the recolor test), and introducing a second one would duplicate what's already there for no benefit.

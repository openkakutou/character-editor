# Localization (i18n) integration approach

**Context:** Backlog item 012 adopts the shared `web-ui-kit` i18next integration layer (`initI18n`, `t`, `<wuik-locale-switcher>`, roadmap decision `023-localization-approach-for-web-ui.md`) so this app's UI strings move into `src/i18n/en.json`/`fr.json` and the user can switch language live, without a page reload, with the choice persisted across reloads. This exact feature already shipped identically in five sibling repos (`stage-viewer-web`, `stage-editor`, `lifebar-viewer-web`, `lifebar-editor`, `mode-quick-versus`); this decision ports `lifebar-editor`'s/`stage-editor`'s approach — the closest siblings: also write-mode editors with undo/redo, a wizard, and a keyboard-shortcuts panel — to this app's own, larger set of screens (characteristics, sprites, palettes, animations, state/combat logic, commands, export).

**Decision:**
- The app's brand name ("Character Editor") is left untranslated, treated as a proper noun. Raw domain data — a state controller's raw `type`/parameter names, a sprite's group/image (file-order) index, a palette's hex color value, animation frame numeric coordinates, a command's raw input-sequence string — is never passed through translation; only the surrounding UI copy (headings, labels, buttons, status/error messages, accessible names) moves into the catalogs.
- A thin wrapper (`src/i18n/i18n.ts`) mirrors `web-ui-kit`'s own `t(key, defaultValue, vars?)` contract exactly, under this app's own namespace (`"character-editor"`) and its own `localStorage` key (`"character-editor-locale"`, not `web-ui-kit`'s shared default) — every OpenKakutou web app deploys as its own GitHub Pages project site under the same origin, so sharing the default key would leak one app's language choice into every other one. Every call site's `defaultValue` is kept identical, character for character, to the English catalog entry for that key, so a render produces the same text whether or not `initAppI18n` has resolved yet — the existing test suite keeps asserting plain English text unchanged.
- `initAppI18n` is only ever called from the real bootstrap (a new `mount()` in `main.ts`), awaited before the first `renderApp` call — never from `renderApp` itself, which stays synchronous so tests can keep calling it directly.
- Live locale-switching is split by how much state a re-render would otherwise destroy, per screen, the same principle `stage-editor`'s own decision `008` applies:
  - Screens with no locale-sensitive state a full re-render would lose (characteristics editor, state editor, palette editor's static chrome, the new-character wizard) are simply re-invoked from `main.ts`'s own `onLocaleChange` subscription, from the data it already holds.
  - Screens holding session-important state a full re-render would destroy or reset — the character file input's per-slot status/errors, the sprite browser's pending edit overlay, the animation editor's expand/Clsn-panel-open state and in-progress playback, the command editor's per-row validation, the export panel's last-computed result, the shortcuts screen's collapsed/expanded state — each subscribe to `onLocaleChange` internally and re-format only their own already-shown text in place from a small stored status descriptor (a tagged kind plus its raw parameters), never a pre-formatted string, mirroring `lifebar-editor`'s own `Status` pattern.
  - The Undo/Redo toolbar buttons' text and `aria-label` are retranslated directly by `main.ts` (the only place that knows both the translated base label and the button element), not by re-running any shortcut-binding helper — this app has no per-action shortcut-hint `title` to keep in sync (see the next point).
  - Keyboard shortcut action labels registered with the shared `ShortcutManager` (shown inside `<wuik-shortcuts-panel>`'s own rebind list) stay hardcoded English, matching `lifebar-editor`'s and `stage-editor`'s own identical, already-shipped precedent — `web-ui-kit`'s `ShortcutManager`/`<wuik-shortcuts-panel>` has no supported way to update a registered action's label after the fact; a pre-existing gap accepted there, not a new one introduced here.
- `main.ts` additionally sets `document.documentElement.lang` to the resolved locale on every locale change (init and switch alike) — a small, purely additive correctness fix (assistive technology needs the real `lang` attribute to select the right pronunciation) that the five sibling repos' own ports of this feature did not yet include; safe to add here since it changes no other test-visible behavior.
- Pluralized fragments are phrased with an inline ternary suffix computed in code (e.g. `"Deleted {{count}} sprite{{suffix}}"`, `vars: { count, suffix: count === 1 ? "" : "s" }`), the same minimal approach `stage-editor` used, rather than i18next's automatic plural-key suffixing.

**Reason:** Matching each screen's re-render strategy to how much state it owns is what keeps this feature from regressing the sprite browser's pending-edit overlay, the animation editor's mid-drag Clsn state, and the export panel's last-computed result, while keeping the existing, already-large test suite passing with minimal, surgical edits — the fallback-mirrors-default-value property is what makes that possible for the majority of existing tests.

**Rejected alternatives:**
- *Re-run every screen's render function wholesale on every locale change, uniformly* — rejected: the sprite browser's pending edits, the animation editor's mounted playback/mid-drag state, and the export panel's last-computed result are exactly the state a wholesale re-render can't tell apart from a first mount, and would visibly reset or silently discard unsaved-but-uncommitted work.
- *Translate the shared `ShortcutManager` action labels too, via a live re-registration on locale change* — rejected as out of scope for this item, the same reasoning `stage-editor`'s decision `008` already gives: inventing a way to do this would be a `web-ui-kit`-level change, not this app's own.
- *A single app-wide `aria-live` region announcing every locale switch, on top of each screen's own existing status regions* — rejected as a scope addition beyond what any of the five shipped sibling apps included; each screen's own already-existing `role="status"`/`aria-live` regions already announce their own retranslated content, and a second, app-wide announcement would be a new pattern introduced here first, better proposed as its own `web-ui-kit`-level backlog item if wanted org-wide.
- *Sharing `web-ui-kit`'s default `wuik-locale` storage key* — rejected for the same cross-app-origin-collision reason every sibling app rejected it.

# character-editor — Codebase index
> Generated by /vibe:sync on 2026-09-18. Re-run to update.

## Modules
- [`modules/app.md`](modules/app.md) — application entry point, mounts the app into the DOM as a `web-ui-kit` app shell (toolbar, Undo/Redo, unsaved-changes indicator) plus the character file input, the new-character wizard, the always-visible "Keyboard shortcuts" screen, the characteristics editor, the sprite browser, the palette editor, the state editor, the animation editor, the command editor, and the export panel
- [`modules/input.md`](modules/input.md) — the character file input: folder selection only (item 014) — gathers a picked/dropped folder's files, finds its `.def` candidate(s) (auto-picking a lone one, asking the user among several), learns which sibling files it references via a narrow local `[Files]`-section read, resolves each by basename against the folder listing, and loads the character through the WASM bridge; also renders the folder-picker + drag-and-drop UI
- [`modules/document.md`](modules/document.md) — in-memory representation of the currently loaded character, for editor screens to read from and write back to via shared patch/append helpers
- [`modules/editors.md`](modules/editors.md) — screens that edit an already-loaded character: the characteristics editor (item 003) and the state/combat logic editor (item 007) — browse StateDefs, add/edit/remove/reorder their Controllers, flagging a blank-type controller as unsupported
- [`modules/sprites.md`](modules/sprites.md) — the sprite browser (item 004): browse, import, replace, delete sprites against an in-memory edit overlay, not yet persisted
- [`modules/palettes.md`](modules/palettes.md) — the palette editor (item 005): edit a 256-color palette, load/save it as `.act`, live-recolored sprite preview, semantic-index storage converted to real file order at exactly two boundaries
- [`modules/animations.md`](modules/animations.md) — the animation editor (item 006): create/edit animations and frames, add/drag/resize/delete Clsn1/Clsn2 boxes with a live preview overlay, play/pause/step playback
- [`modules/commands.md`](modules/commands.md) — the command editor (item 008): view/edit `.cmd` commands (name, input sequence, timing), map one to a target combat state via a `ChangeState` controller keyed by the command's name; a blank/duplicate name, blank input, or unknown target state is excluded from the committed model until fixed
- [`modules/wasm.md`](modules/wasm.md) — bridge to the `character` WASM module: typed `loadCharacter`/`resolveSpritePixels`/`loadCmd`/`saveDef`/`saveAir`/`saveCns`/`saveCmd` wrappers plus the full `CharacterData`/`CommandFile` TypeScript vocabulary
- [`modules/save.md`](modules/save.md) — Save/Export (item 009): serializes the current character back to downloadable `.def`/`.air`/`.cns`/`.cmd`/`.zss` files, byte-exact where unedited, blocked with a precise reason on a pending sprite edit or a serialize error
- [`modules/scripts.md`](modules/scripts.md) — dev-tooling scripts, e.g. downloading the `character` WASM release build
- [`modules/history.md`](modules/history.md) — the shared undo/redo history (item 010), built on `web-ui-kit`'s `CommandStack`, plus the `beforeunload` unsaved-changes guard driven by its own separate "dirty" flag
- [`modules/wizard.md`](modules/wizard.md) — the new-character wizard (item 010): builds a minimal character (blank or "basic" template) via the same WASM save-then-load round trip real characters go through, indistinguishable from an import once created
- [`modules/shortcuts.md`](modules/shortcuts.md) — the keyboard-shortcut layer (item 011): registers this app's actions on `web-ui-kit`'s shared `ShortcutManager`, one global keydown listener that clicks the matching `data-action` button, and an always-visible screen hosting the shared `<wuik-shortcuts-panel>`
- [`modules/i18n.md`](modules/i18n.md) — this app's own localization setup (item 012): a thin wrapper around `web-ui-kit`'s shared i18next integration layer (own namespace, own `localStorage` key), `en.json`/`fr.json` catalogs, and the `t(key, defaultValue, vars?)` every other module's DOM layer reads its strings through

## Observed patterns
- The DOM-building logic of a screen/component is a pure exported function (`renderApp(root, version, installedWebUiKitVersion, options?)`, `renderCharacterFileInput(root, options)`) taking its target element and data/callbacks as parameters, kept separate from the module-level bootstrap — same "inject external effects for testability" shape as the WASM bridge and download script, applied here to DOM construction instead of `fetch`
- Any app-level visual value (typography hierarchy, spacing, color) is expressed only through `@openkakutou/web-ui-kit`'s `--wuik-*` CSS custom properties, never a literal px/hex value — see `.vibe/decisions/001-web-ui-kit-adoption-scope.md`
- Inline error/invalid-state text uses `--wuik-color-text`, never `--wuik-color-danger`, matching `web-ui-kit`'s own accessibility-verified convention (its `.vibe/decisions/009`); the invalid state itself still signals non-verbally via a danger-colored border
- TypeScript with `strict`, `noUnusedLocals`, `noUnusedParameters` enabled (`tsconfig.json`)
- Explicit `.ts` extensions on relative imports (`allowImportingTsExtensions`)
- Test files co-located with source as `*.test.ts`/`*.test.mjs`, using Vitest + jsdom
- Dev-tooling scripts outside the app bundle live in `scripts/` as plain `.mjs` (not bundled/type-checked by `tsc`, whose `include` is scoped to `src/`)
- CLI-style scripts return an exit code from a testable `main(argv, overrides)` function rather than calling `process.exit` directly, and inject external effects (`fetch`, output dir) as parameters for testability — the same shape reappears in `src/wasm/bridge.ts` (`fetchWasmExecSource`/`fetchWasmBytes`) and `src/input/character-file-input.ts` (`readFileBytes`)
- `wasm_exec.js` is executed via `new Function(source)()` rather than a `<script>` tag or dynamic `import()`, so the same loading code works identically in a real browser and under jsdom/Node
- File bytes are read via `FileReader#readAsArrayBuffer` rather than `Blob#arrayBuffer()` for the same real-browser/jsdom parity reason — the pinned jsdom version does not implement `Blob#arrayBuffer()` at all
- Fixture-driven tests that exercise the real WASM module pin expected values obtained by running the actual module once against the fixture, reusing `character-viewer-web`'s minimal `.air`/`.sff`/`.cns` fixtures (`src/wasm/testdata/`) rather than depending on a sibling checkout at test time
- A set of related, config-driven items (the 6 accepted file kinds) is expressed as one ordered array (`ALL_FILE_KINDS`) consumed by both the pure logic and the DOM view, rather than duplicated as separate hardcoded lists in each — so a future added kind doesn't require reworking rendering code
- Module-level, in-process application state with no external effect to substitute in tests (`src/document/character-document.ts`) is a plain get/set pair with a test-only reset function, the same "reset between tests" shape `src/wasm/bridge.ts`'s `resetWasmBridgeForTests` already established for its own memoization
- An editor screen never imports the document store directly — it takes an `onChange`/`onLoaded`-style callback and lets `app` (the composition root) wire it to the store, the same decoupling `input` already established; this keeps `characteristics-editor.ts` testable with a plain fixture and a spy, no document-module setup needed
- Where `web-ui-kit` has no component yet for a needed UI primitive (a generic text input), the stopgap is a plain native element styled with the same `--wuik-*` tokens and reusing `web-ui-kit`'s own documented state contracts (`is-invalid`/`aria-invalid`/danger border, inset focus ring) rather than inventing a new visual language — see `.vibe/decisions/003`, and `character-viewer-web`'s `<wuik-viewport>` precedent for the same pattern
- A list of editable entries (e.g. `stateFiles`, `palettes` rows) updates one DOM node's own state/classes in place on blur/input rather than re-rendering the whole list, so editing or leaving one row can never steal focus by replacing the DOM node the user is actively interacting with
- Session-only editing state that must survive re-renders but never needs a full external re-render to reflect its own changes (`sprite-browser.ts`'s pending `SpriteEdit[]`) is kept as a local closure variable, reported upward via a callback (`onSpriteEdit`) for the caller to persist, rather than requiring the parent to re-invoke the whole render function on every edit — the same decoupling `editors` already established, one level more self-contained
- A destructive action with a variable-risk warning (deleting a sprite referenced by animation frames) always requires an explicit confirm step, even when the reference count is 0, and offers a separate, differently-labeled Cancel control rather than a same-button double-click — a same-button toggle is an accidental-double-click/repeated-Enter trap for a destructive action
- A browser effect `jsdom` cannot exercise at all — not just undesirable to hit in a unit test, but genuinely unimplemented (`HTMLCanvasElement.getContext("2d")`, `createImageBitmap`) — is taken as an injectable option with a real default, verified separately by a real-browser pass instead of by the unit test suite (`sprite-browser.ts`'s `drawPixels`, `image-decode.ts`'s `decodeImageFile`/`extractPixels`)
- A `<wuik-viewport>`/similar custom element's own methods (`resetToFit()`) are called through an optional-chaining guard (`el.resetToFit?.()`) rather than assumed present, since this project's test environment never registers `@openkakutou/web-ui-kit`'s custom elements — a plain jsdom element has no such method, so the guard makes it a silent no-op under test without needing a separate injectable option just for this one call
- A byte-order (or similarly index-permuting) conversion between an internal, domain-natural representation and an external file's own on-disk layout is written once as a single function proven to be its own inverse, rather than a separate "to file order"/"from file order" pair — every call site that needs either direction calls the same function, foreclosing the classic bug of two subtly different reversal formulas drifting apart (`palette.ts`'s `reversePaletteByteOrder`, `.vibe/decisions/005`)
- `<wuik-button>`'s `disabled` state is read from `hasAttribute("disabled")` on the host custom element, not a `.disabled` IDL property a plain `document.createElement` call never gets for a custom element — toggling it needs `setAttribute`/`removeAttribute`, not a property assignment that would silently do nothing
- A grid of many identical, individually-editable cells (a 256-swatch palette grid) updates one cell's own DOM in place after an edit, rather than rebuilding the whole grid — the same "never steal focus by replacing the node the user is interacting with" precedent already established for editable list rows, applied here to the shared input control (`<wuik-color-picker>`) that must never be torn down mid-interaction
- A screen reusing another already-tested screen's own effect (`palette-editor.ts` importing `sprite-browser.ts`'s exported `defaultDrawPixels`) does so directly rather than re-implementing an identical canvas-draw call, once that function is already exported for its own module's tests to inject
- A boundary-sensitive action (reorder move-up/down at a list edge) is guarded by its own handler re-checking the boundary condition, never solely by the triggering button's `disabled` attribute — found by real-browser runtime verification (`state-editor.ts`'s move handlers), the same "belt-and-braces, don't trust the DOM attribute alone" precedent `palette-editor.ts`'s own disabled-click guard already established
- A classification computed from a value that the user can also edit (an "unsupported" controller's blank `type`) is fixed once when the row is first built, never re-derived from the live/edited value on every render — re-deriving it would let editing a field change whether that same field is editable, a self-referential, data-loss-risking state transition (`state-editor.ts`, `.vibe/decisions/006`)
- A destructive action's confirm requirement scales with its blast radius rather than applying uniformly: removing one list item needs no confirmation, removing a whole group of them does, showing the count about to go with it — `sprite-browser.ts`'s per-sprite reference-count warning and `state-editor.ts`'s per-StateDef controller-count warning are two applications of the same instinct, neither requiring the other's exact reference-counting mechanism
- An interactive editing surface that can also be reached by keyboard offers the exact same commit path both ways rather than a drag-only feature with keyboard as an afterthought — `animation-editor.ts`'s Clsn boxes are numeric-input, arrow-key-nudge, and pointer-drag, all three funneling through the same pure geometry functions (`animation-logic.ts`'s `moveClsnBox`/`resizeClsnBox`/`setClsnBoxBounds`), so none of the three paths can silently drift from the others
- A drag interaction (pointerdown → pointermove× → pointerup) mutates the dragged element's own inline style live during the move and commits to the data model (plus a full re-render) exactly once, on pointerup — never on every intermediate `pointermove` — found by real-browser runtime verification that a per-move full re-render is both visibly janky and invalidates any element reference a caller holds mid-drag (`animation-editor.ts`'s `wireMoveDrag`/`wireResizeDrag`)
- A visual overlay that must stay pixel-aligned with a zoomable/pannable preview is placed as a DOM sibling *inside* the same `<wuik-viewport>` as the content it overlays, never as a separately-positioned layer — the viewport's own existing pan/zoom CSS transform then applies to both without this app tracking that transform itself (`animation-editor.ts`'s Clsn box overlay, `.vibe/decisions/007`)
- Per-`root` UI-only state that must survive a caller re-invoking a render function repeatedly against the same DOM container (e.g. `app` re-rendering `animations` on every sprite-browser edit to keep its sprite-existence check current) is kept in a module-level `WeakMap<rootElement, state>` rather than a closure-local variable that would reset on each call — `animation-editor.ts`'s expand/Clsn-panel-open state
- A UI action's state that can only sensibly exist while some other independent state is active (an in-progress playback and a mid-drag Clsn edit both targeting the same preview) resolves the conflict by pausing the first automatically when the second starts, rather than blocking the second or requiring the user to remember to pause first (`animation-editor.ts`)
- A screen whose data isn't reachable through the already-loaded `CharacterData` at all (`.cmd`, since it isn't wired into the WASM `load` contract) owns its own WASM parse call against raw bytes handed to it directly, rather than waiting for a caller to pre-parse and hand over a finished model — the same "editor owns the WASM call for the raw bytes it's given" shape `resolveSpritePixels` already established, extended here to the screen's own *initial* load, not just an on-demand action (`command-editor.ts`'s `loadCmd` call)
- A cross-referential link between two edited collections (a command row and the specific controller inside a separate array that implements its state mapping) is recomputed by removing every row's *previous* link then re-adding its *current* one on every commit, never patched incrementally — this is the one strategy that can't leave a stale reference behind after a rename, a newly invalid row, or a cleared mapping, at the cost of redoing unrelated rows' links on every keystroke, which is cheap here (`command-editor.ts`'s `commitAll`, `.vibe/decisions/008`)
- Two fields in the same edited row can validate independently with independent inline errors (a command's Name/Input/Target-state) while still gating the same all-or-nothing commit — the row is excluded from the committed model if *any* field is invalid, but each field's own error message names only that field's problem, never a generic "this row is invalid" (`command-editor.ts`, `.vibe/decisions/008`)
- A screen whose freshness depends on several other screens' cumulative state, but whose own computation is too expensive to fire on every one of their keystrokes (Export calling several WASM `saveX` round trips), computes once on its own render and again only on its own explicit action — never wired into the other screens' `onChange` the way `animations`' live re-render is — reading the shared document store fresh each time so the explicit action never returns a stale result (`export-panel.ts`, `.vibe/decisions/010`)
- A multi-part operation that writes several independent outputs (Export's `.def`/`.air`/`.cns`/`.cmd`) treats any one part's failure as blocking the whole operation, not just that part — no result is presented to the user until every part that will be produced has actually succeeded, so a partial/inconsistent bundle can never be offered as if it were complete (`character-export.ts`, `.vibe/decisions/009`)
- A caller-visible mutator that must be undoable snapshots its before/after state as a deep clone rather than a live reference, whenever anything upstream might mutate a nested object in place before committing it — `document`'s `updateCharacterFields` does this specifically because `state-editor.ts`/`animation-editor.ts` mutate a StateDef's controllers or a Frame's Clsn boxes in place before calling `onChange` with the same array reference, which would otherwise make "before" and "after" the same object by the time the snapshot runs (`.vibe/decisions/011`)
- A load-time "seed the store with what was just parsed" call is kept structurally distinct from a genuine user edit, even when both would otherwise go through the same callback — `command-editor.ts`'s mount-time `onChange(commandFile, true)` carries an explicit `isInitialLoad` flag so the caller can route it to a non-undoable seed (`document.seedCommandFile`) instead of the real, history-recording edit path (`setCommandFile`); conflating the two either pollutes every character's history with a phantom first entry, or (once a screen can be re-mounted more than once, as item 010's undo/redo does) silently discards real edits and corrupts the redo stack on every re-mount
- A screen that manages its own local undo/redo commands (rather than routing edits through a caller `onChange`) still pushes onto the *same* shared history everyone else uses, and reports every local push to its caller via a dedicated callback (`onHistoryPush`) purely so an external toolbar's enabled/disabled state can stay in sync — `palette-editor.ts` is the only screen shaped this way, since its data was never part of `CharacterData` to begin with
- A history-recording command's own `do`/`undo` never touch the DOM directly, even when the same operation, driven normally (typing, clicking a swatch), does update the DOM in place — the DOM update stays exactly as fine-grained as before item 010 introduced undo/redo, and only an *external* trigger (an Undo/Redo click, via a returned handle's `refresh()`) does a coarser full rebuild, since `CommandStack.push()` calls `do()` synchronously and a DOM-touching `do()` would otherwise rebuild the DOM on every single normal edit too (`character-document.ts`'s `applyCharacterSnapshot`, `palette-editor.ts`'s `recordChange`)
- Multiple document-backed editor screens are re-rendered together from a single fresh `CharacterData` in response to one external trigger (an Undo/Redo click), rather than each screen owning its own "resync from external state" logic — cheaper to reason about than N screens each independently detecting drift, at the cost of a full rebuild of all of them on every click; a screen that can't safely support being re-mounted this way (the command editor, which would otherwise silently discard real edits by re-parsing raw bytes) is excluded from that shared re-render entirely rather than special-cased within it (`main.ts`'s `renderDocumentBackedEditors`/`onHistoryChange`)
- Two DOM elements meant to be visually/semantically distinct but sharing an otherwise-identical rendering pattern (a loaded character's own Name field vs. the new-character wizard's own Name field) get distinct `data-*` attribute values even when a shared literal would "just work" by coincidence — found by real-browser/test-driven verification that a generic selector silently matches whichever one happens to sit first in DOM order, corrupting an unrelated test or a keyboard/automation flow with no error of any kind (`new-character-wizard-view.ts`'s `data-field="wizard-name"`, distinct from `characteristics-editor.ts`'s `data-field="name"`)
- A new global capability that must trigger an existing action (a keyboard shortcut for Undo/Add StateDef/etc.) is wired as "resolve to an id, then `.click()` the one element already carrying that `data-action`" rather than a second call into the action's own handler — `global-shortcut-listener.ts` never duplicates a button's logic, so a shortcut can never drift from what clicking the button actually does; each shortcut's registered id is chosen to equal that button's existing `data-action` value specifically to make this mapping trivial
- `@openkakutou/web-ui-kit` ships no type declarations at all (confirmed again for `ShortcutManager`/`ShortcutAction`/etc.) — every named import from it needs a matching ambient declaration hand-added to `src/types/web-ui-kit.d.ts`, mirroring the real package's shape, not just the few names already used by earlier items
- A normalization/classification algorithm the shared `web-ui-kit` component computes internally but doesn't export (its keyboard-combo string format, e.g. `"Ctrl+Shift+S"`) is re-implemented locally as its own small pure function when this app needs to compute the same value itself (`global-shortcut-listener.ts`'s `normalizeShortcutEvent`), rather than reaching into the package's private internals — documented at the call site as intentional duplication of an unexported detail, not an oversight
- A default keyboard-combo choice avoids `Ctrl+Alt+*` specifically because AltGr (used to type accented/special characters on many European keyboard layouts) is reported by browsers as `ctrlKey + altKey` both true — `Alt+Shift+*` is used instead for this app's own "Add" shortcuts, sidestepping that overlap entirely
- `HTMLElement.isContentEditable` is unimplemented in this project's pinned `jsdom` (stays `undefined`, not even a boolean, even after setting the `contenteditable` attribute) — checked via the raw attribute instead (`global-shortcut-listener.ts`'s `shouldIgnoreGlobalShortcut`), the same "unimplemented browser effect" category as `HTMLCanvasElement.getContext`/`DataTransfer`
- Calling a render function with the *shared* top-level element (`main`) as its `root` argument, rather than a dedicated sub-container, means that function's own `root.replaceChildren()` wipes out any sibling content already appended to `main` before it ran — found by real-browser runtime verification when the "Keyboard shortcuts" screen, appended to `main` before `renderCharacterFileInput(main, ...)` ran, was silently erased by that call; fixed by rendering screens that don't own a dedicated container strictly after any call passed `main` itself
- A screen retranslating on locale change matches its re-render strategy to how much of its own session state a wholesale rebuild would destroy, the same instinct as the undo/redo re-render split: no locale-sensitive state at all (`characteristics-editor.ts`/`state-editor.ts`) is simply re-invoked by `app`'s own subscription; a screen whose whole subtree already rebuilds fresh from held closure data on every call (`command-editor.ts`'s `renderList()`, `palette-editor.ts`'s `renderBody()`) just gets that same call again; a screen with real state a rebuild would lose (`sprite-browser.ts`'s expanded groups/current preview, `export-panel.ts`'s last-computed result) stores that state explicitly and subscribes to `onLocaleChange` internally, reformatting already-shown text from it without re-running the WASM call or file read that produced it in the first place (`.vibe/decisions/015`)
- `t(key, defaultValue, vars?)`'s `defaultValue` argument is deliberately kept character-for-character identical to that key's `en.json` entry everywhere it's called — this is what lets the fallback path (before `initAppI18n` has resolved, e.g. in every existing test) render the exact same English text a real translation would, so adding localization needed zero changes to almost every pre-existing test's own assertions
- A label element wrapping a nested native control (`<label>Group<input></label>`) that must also be retranslatable in place uses a bare `Text` node for its own visible word, inserted before the control, rather than `label.textContent = "..."` — the latter would delete the nested control on every retranslation. Used wherever a label needs both: `new-character-wizard-view.ts`'s `nameLabelText`, `sprite-browser.ts`'s `groupLabelText`, `palette-editor.ts`'s `uploadLabelText`
- A screen `app` can re-mount more than once per page (the new-character wizard replacing an already-loaded character) tracks its own locale-change subscription's unsubscribe function in a module-level variable, called at the very top of its own render function before registering a fresh one — otherwise a second mount's subscription would stack on top of the first's rather than replacing it (`sprite-browser.ts`, `palette-editor.ts`, `command-editor.ts`, `export-panel.ts`)
- A collapsible-panel screen's expand/collapse state must be lifted into a per-`root` `WeakMap` (`animation-editor.ts`'s pre-existing `uiStateByRoot`, now `state-editor.ts`'s own `expandedByRoot`) rather than a closure-local `Set`, whenever the caller (`app`) can legitimately re-invoke the same render function against the same root more than once per session (an Undo/Redo click, a locale change) — a closure-local `Set` resets to empty on every such call, silently collapsing whatever the user had open; found by real-browser runtime verification of the locale-switch feature, where `state-editor.ts` had the closure-local version and visibly lost its expanded StateDef on a locale switch (an Undo/Redo click already triggered the identical loss, unnoticed until this pass)
- A generic, domain-agnostic browser-API-workaround module (folder-selection gathering: a `webkitdirectory` picker's `FileList` plus a dropped folder's recursive `DataTransferItem.webkitGetAsEntry()`/`FileSystemDirectoryReader` walk) is ported near-verbatim from a sibling repo (`stage-editor`/`lifebar-editor`) that already shipped and real-browser-verified the identical shape (item 014's `folder-entries.ts`), rather than re-derived — the non-standard browser types (`FileSystemEntry`, `DataTransferItem`) are modeled as minimal `*Like` interfaces covering only the members actually read, so the walk logic is unit-testable against plain mock objects even though jsdom implements neither API at all
- When the WASM boundary itself can't answer a question a sibling app's own bridge can (`character`'s `load` call needs all 4 required files' bytes at once, unlike `stage`/`lifebar`'s own bridges, which can parse a `.def` alone and learn its referenced filenames from the result) — a deliberately minimal, narrowly-scoped local text parse of just the relevant section (`def-files-section.ts`'s `[Files]`-section read, 4 keys) is written instead of reaching for the format's own full parser, with the reused key names checked directly against the source Go library's own parser first rather than guessed
- A referenced filename is resolved against an already-gathered folder listing by basename — exact case first, case-insensitive fallback second, more than one match reported as ambiguous rather than silently picked — ported directly from `stage-editor`/`lifebar-editor`'s own established resolution rule (`character-file-input.ts`'s `resolveReferencedFile`), not re-derived, since basename resolution has no domain specifics of its own
- An optional kind's ambiguity discovered only after successfully resolving everything required (item 014's `.zss`, found by extension since the `.def` format has no key that references one) is surfaced as an optional field on the success result (`zssAmbiguousCount`) rather than its own terminal failure state — extending item 002's original "an optional kind's problem never blocks an otherwise-complete required load" rule from same-gesture duplicates to a resolution-time ambiguity
- A `hidden`-toggled element given its own class-level `display` CSS value (`.file-input__selection { display: flex }`) can silently lose the `hidden` attribute's effect — the UA stylesheet's `[hidden] { display: none }` and an author class selector have equal specificity, and author rules win at equal specificity, so the class's `display` silently overrides `hidden` — found only by real-browser runtime verification (a jsdom-based test never renders CSS at all), fixed with a higher-specificity `.file-input__selection[hidden] { display: none }` override; any future `hidden`-toggled element that also carries its own unconditional `display` value needs the same override

# Module: commands
**Role:** The command editor (item 008): view/edit an already-loaded character's `.cmd` commands (name, input sequence, timing overrides) and optionally map each one to a target combat state from `character.stateDefs`. Unlike every other editor screen, this one owns its own WASM call (`wasm.loadCmd`) rather than reading an already-parsed field off `CharacterData`, since `.cmd` isn't wired into that type at all — a missing or unparseable `.cmd` file degrades to a visible message plus a usable blank starting point. The command-to-state link is represented the way the real file format does it: a `ChangeState` controller inside the linked always-state, keyed by the command's name (see `.vibe/decisions/008-command-editor-state-link-and-validation-scope.md`). A row with a blank/duplicate name, blank input, or an unknown target state is excluded from the committed model entirely until fixed; loading already-invalid data never discards it. Its own mount (`startReady`) reports the freshly parsed `.cmd` file to `onChange` once, with a second `isInitialLoad: true` argument distinguishing that one-time seed from a genuine edit — the caller (`app`) routes it to `document.seedCommandFile` (no history entry) instead of `setCommandFile` (item 010's undoable path). `app` mounts this screen exactly once per character load, never again on Undo/Redo, since it has no way to resync its displayed rows from an externally-changed `commandFile` — only from re-parsing the original raw bytes, which would otherwise silently discard real edits (see `.vibe/decisions/011` and `docs/architecture.md`'s "Data flow: undo/redo across editors").

**Exports:** `emptyCommandFile(): CommandFile`, `validateCommandRow(name, input, targetStateText, otherNames, availableStateNumbers): CommandRowValidation`, `findLinkedStateNumber(states, commandName): number | null`, `setLinkedState(states, commandName, targetState): StateDef[]`, `renderCommandEditor(root, character, cmdBytes, options): void`, `CommandEditorOptions`
